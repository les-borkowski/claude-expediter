description: Drive a whole feature plan to a reviewable branch — refine the design, split into tickets, then run each ticket through dev-cycle-loop, committing per ticket. Stops for the user to review before merging.
argument-hint: <plan file path or inline plan>

Take this feature plan and drive it to completion on a reviewable branch: $ARGUMENTS

This is the outer sequencer that sits on top of `/dev-cycle-loop`. Where `dev-cycle-loop` runs ONE task and hands back, this command owns the whole feature: refine → question → ticket → branch → drive every ticket → hand back a branch for the user to review. It does NOT merge.

**Framing rules (same discipline as dev-cycle-loop):**
- You (the orchestrator) do NOT edit code yourself. Every code change flows through `/dev-cycle-loop`'s subagents so each stays scoped to its role. You only write plan/ticket artifacts, create the branch, and commit.
- Each ticket brief you pass to `/dev-cycle-loop` is a self-contained contract. Do NOT tell it or its subagents to "read the plan file" — inline the specifics (goal, files, approach, exact verify criteria).
- The backend agents (`feature-implementer`, `test-writer`, `code-reviewer`) declare narrow tool allowlists, so they have `Bash` but no `PowerShell` and no MCP tools — a property of those definitions, not a platform limit (`frontend-dev` inherits both). Give them Bash-syntax build commands.
- **Resolve the build and test commands yourself before writing any ticket brief.** Read `## Build & Test Commands` in the project's `CLAUDE.md` (see the plugin's `SETUP.md` for the contract) and pass the resolved commands inline. If the toolchain lives off `PATH` or the doc pins a version, verify it still exists rather than trusting the written version — versions get bumped in place and a pinned one eventually lies.
- **Don't do lookups yourself.** Writing a self-contained ticket brief needs exact file paths and call sites. Dispatch `quick-lookup` (haiku, read-only) for those instead of grepping in your own context — over a whole feature's worth of tickets that adds up, and this orchestrator's context is the one you most want to keep clean.
- Inside this loop the recipe governs. Superpowers skills are used at the named integration points below; their own triggers do not restructure the loop. Skip any integration point whose skill isn't installed.

**Pacing:** there are exactly two approval gates — the design questions (step 2) and the to-tickets quiz (step 4). After both are cleared, run tickets straight through in auto/batch mode. Only stop early on unresolved review findings after 3 fix iterations, or a genuine blocker.

**Steps:**

1. **Ingest & refine.** Read the plan from the argument (a file path, or inline plan text). Incoming plans are usually already detailed — refine, don't re-plan. Only if the input is thin or ambiguous, fall back to `superpowers:brainstorming` → `superpowers:writing-plans` to firm it up first. Apply the `codebase-design` skill to plan the implementation: identify the deep modules and seams the plan implies, name them with the glossary, and decide the implementation order. For a genuinely hard interface decision, optionally fan out `DESIGN-IT-TWICE` sub-agents and compare on depth/locality/seam placement. For a UI-facing feature, also load the `frontend-design` skill so tickets carry concrete visual direction (typography, layout, component intent) instead of leaving it to improvisation. Write the refined plan to the project's plan directory (`docs/<feature>-plan.md` unless the project's `## Documentation Map` says otherwise).

2. **Ask open questions.** If refinement surfaces decisions only the user can make (ambiguous requirements, competing approaches), use `AskUserQuestion` before going further. *(First approval gate.)*

3. **Create the branch in an isolated worktree.** Derive a `<slug>` from the feature name. Follow `superpowers:using-git-worktrees` Step 0 first: if the session is already in a linked worktree, skip creation and use that path. Otherwise use the native `EnterWorktree` tool — `EnterWorktree({ name: "feature-<slug>" })` — to create branch `feature/<slug>` and switch the session into its worktree; do not drop to raw `git worktree add` while the native tool is available. From this point on, every ticket brief, subagent dispatch, and build-file path must point at the worktree's checkout path (as reported by `EnterWorktree`), not the original checkout. All ticket work commits onto `feature/<slug>` inside this worktree.

4. **Split into tickets.** Invoke the `/to-tickets` skill against the refined plan — local-file mode writes one file per ticket to `.scratch/<feature-slug>/issues/<NN>-<slug>.md` in dependency order, with blocking edges. It quizzes the user and iterates until the breakdown is approved. *(Second approval gate.)*
   - *Fallback:* `/to-tickets` is `disable-model-invocation: true`. If it cannot be invoked here, follow its documented vertical-slice process inline (tracer-bullet slices, blocking edges, expand–contract for wide refactors) and write the same `<NN>-<slug>.md` files yourself, then quiz the user for approval.

5. **Drive tickets (auto/batch).**

   **Before the first ticket: if any ticket in the plan is UI-facing, start the app once, here.** Browser verification needs a running app, and starting it is the most expensive thing in the frontend cycle — a cold backend that loads a large production dataset can spend minutes doing it. Starting once per *feature* instead of once per *ticket* pays that cost a single time.
   - Use the commands in the project's `## Dev Servers` section, preferring its lightweight/fixture-backed mode. Run them in the background from the worktree checkout, and note the URLs.
   - Do **not** use a skip-the-build startup flag for this first start: where a project has one, its modules resolve from a shared local artifact cache, and a stale artifact there boots normally while silently serving old code. A worktree's cache holds whatever branch last built, so the first full build in a new worktree is mandatory.
   - `/dev-frontend-cycle-loop` will find the servers already reachable and skip its own startup step. Leave them running across tickets, and tear them down only at step 7.
   - **A ticket that changes server-side code invalidates the running server.** After committing such a ticket, restart it before the next UI-facing ticket, or the browser check will exercise stale code.

   Work the dependency **frontier** — any ticket whose blockers are all committed (a linear chain runs top to bottom). For each ticket:
   - Note the current `HEAD` as this ticket's **fixed point** (base commit).
   - Build a self-contained brief inline from the ticket file plus the refined-plan context: goal, exact file list, approach, and exact verify criteria. Mark the ticket TDD or `model: opus` reviewer if the plan calls for it.
   - **Route by ticket shape:** run `/dev-cycle-loop <brief>` for non-UI tickets, `/dev-frontend-cycle-loop <brief>` when the acceptance criteria are visual or interaction-based (it dispatches `frontend-dev`, which verifies in a real browser inside the implementer), or `/docs-cycle-loop <brief>` for a docs-only ticket — one marked `Type: docs`, or whose entire deliverable is prose in the documentation surfaces. Do not send a docs ticket through the dev loops: their test and build steps have nothing to do, and `code-reviewer`'s checklist is entirely code conventions. For a full-stack ticket, prefer splitting it at step 4; if it stays whole, run the backend slice through `/dev-cycle-loop` first, then the UI slice through `/dev-frontend-cycle-loop`. Either way, wait for it to return.
   - **Complexity escalation** — if the ticket is complex (crosses backend + frontend, adds a new module / interface / screen, touches many files, or is flagged complex in the plan), after the cycle returns clean do an extra review yourself: read the ticket diff (`git diff <fixed-point>...HEAD`), and run the `/code-review` skill with the fixed point = this ticket's base commit and the spec source = the ticket file. Send any new findings back through the cycle loop (respect its 3-iteration bound). This escalation is for **code** tickets; a docs ticket's equivalent is `/docs-cycle-loop`'s own fact-check plus its stale-reference sweep — don't add a `/code-review` pass on prose.
   - On a clean result, **commit** the ticket's changes onto `feature/<slug>` with a message referencing the ticket number/title. If a background security or review hook rewakes you with findings, address or acknowledge them before advancing. Then advance to the next frontier ticket without pausing.
   - **Record the docs impact.** After the commit, append one line to `.scratch/<feature-slug>/docs-impact.md` naming what this ticket changed that a living overview, a `CLAUDE.md`, or a README will need to reflect — or "none". The cycle loops report this in their handback; just carry it across. This is a durable artifact on purpose: a docs sweep late in a long feature must not depend on your context surviving compaction, and `/docs-cycle-loop` step 1 reads it to scope the sweep.

6. **Escalate, don't spin.** Stop and report to the user only when a ticket's findings remain after 3 fix iterations, or a genuine blocker appears (ambiguous requirement, failing infrastructure). Otherwise run to completion.

7. **Final report — do NOT merge.** Summarise: the branch name, the worktree path, each ticket completed with its test result and final review status, and any escalations. Then use `superpowers:finishing-a-development-branch` to present the structured completion options (merge locally / push + PR / keep the branch / discard) — but never merge or push without the user choosing it. Once the user has chosen, use `ExitWorktree` to leave the worktree: `keep` if they want to keep iterating there or review it further, `remove` once it's been merged/pushed or they discard it.
   - **Stop the dev servers you started in step 5** before removing a worktree. Note that stopping a background build-tool task does not necessarily kill the process it forked — a forked server keeps its port bound and may hold a database or lock file open, so the next boot fails. Find the PID by port and kill it explicitly, checking first that it isn't another session's server.
