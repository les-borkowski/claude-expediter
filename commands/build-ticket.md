Run this single, self-contained task through the full subagent cycle with a bounded fix-loop: $ARGUMENTS

This command executes ONE unit of work (typically one plan phase or sub-task) and returns to you at the end — it does NOT advance to the next task. The caller owns sequencing, the eval gate, and pausing for go-ahead.

**Rules for the whole cycle:**
- You (the orchestrator running this command) do NOT edit code yourself. Every change goes through a subagent so each stays scoped to its role.
- The task brief above is the contract. Do NOT tell subagents to "read the plan file" — pass them the specifics they need (goal, files, approach, exact verify criteria) inline in the brief.
- Give agents an explicit file list and the `git diff`, never "look at the changes."
- **Don't do lookups yourself.** When you need a file list, a symbol's location, or the call sites of something before you can write a brief, dispatch `quick-lookup` (haiku, read-only) instead of grepping in your own context. It is cheap and its output is exactly the path:line list a brief needs.
- The three agents this command dispatches (`feature-implementer`, `test-writer`, `code-reviewer`) declare narrow tool allowlists, so they have `Bash` but no `PowerShell` and no MCP tools. That's a property of those definitions, not a platform limit — a subagent inherits the session's MCP tools whenever it doesn't specify an allowlist (see `frontend-dev`, which does have them). Give these three Bash-syntax build commands.
- **Resolve the build and test commands yourself before writing any brief.** Read the project's `CLAUDE.md` section `## Build & Test Commands` (see the plugin's `SETUP.md` for the contract) and pass the resolved commands inline. If the project's toolchain lives off `PATH` or pins a version, **verify it still exists** (`ls` the toolchain directory) rather than trusting a version written into a doc — versions get bumped in place and a pinned one eventually lies. Pass the values you actually resolved, set inline if the environment doesn't already provide them.
- Inside this command the recipe governs. Superpowers skills are used at the named integration points below; their own triggers do not restructure the loop. Skip any integration point whose skill isn't installed.

**Steps:**

0. **Isolate (standalone runs only).** Skip this step when nested inside `/drive-tickets` or `/build-feature` (it already sets up an isolated worktree per `superpowers:using-git-worktrees`, and this cycle inherits that session's working directory) or when the session is already in a linked worktree. Otherwise, follow `superpowers:using-git-worktrees` Step 0 (detect existing isolation), then use the native `EnterWorktree` tool to create/switch into one before Step 1 — do not drop to raw `git worktree add` while the native tool is available. If isolating, every file path and build-file path given to subagents in the steps below must point at the worktree's checkout, not the original checkout.

1. **Implement** — dispatch `feature-implementer` with the task brief. Wait for it to finish; note the exact files it created/modified and the test output it reported.

2. **Test and review — dispatch both together, in one message.** `test-writer` and `code-reviewer` are independent given step 1's diff: the reviewer finds correctness bugs in the implementation, and it does not need the tests to exist to do that. Running them concurrently removes a serial leg from every ticket.
   - **`test-writer`** — give it the exact changed-file list from step 1 plus the specific behaviours / verify-criteria from the brief that need coverage, not the raw task description. Confirm it ran the tests and capture the actual pass/fail output.
   - **`code-reviewer`** (this plugin's agent — disambiguate if another installed plugin ships a same-named one) — give it the file list and the `git diff` from step 1, not "review the changes." **Tell it explicitly that tests are being written concurrently and that it must not report missing test coverage** — otherwise it will flag an absence you already have an agent fixing, and you'll waste a fix iteration on a phantom finding. If the brief specifies an opus reviewer for this task, dispatch with `model: opus`.
   - **Exception — TDD tasks run serially.** If the brief marks the task TDD, `superpowers:test-driven-development` governs: tests first and confirmed failing (red), *then* step 1 implements to green. There is no parallelism to win there because step 1 depends on the tests.
   - Once both return, do one **coverage pass**: resume the same `code-reviewer` (see the fix-loop below) with just the test files `test-writer` added, and ask only whether the new logic is actually covered. This is a short follow-up on a warm context, not a second full review.
   - For a complex diff (or when the brief asks for a fuller review), you may run the `/code-review` skill instead of — or in addition to — the `code-reviewer` agent: it does a two-axis Standards + Spec review via parallel sub-agents. Pass it the fixed point (this task's base commit) and the spec source (the task brief or ticket file). Note the `code-reviewer` *agent* has no Skill tool, so `/code-review` must be run here at the orchestrator level, not inside the agent. Feed its findings into the same fix-loop below.

3. **Fix-loop (max 3 iterations):**
   - **Verify findings via `verifier`, not in your own context.** Dispatch `verifier` in finding-check mode with the findings, the file list and the diff; forward only the ones it marks `real`, dropping the rest rather than commissioning performative fixes. If a verdict looks wrong to you on its face, that's the moment to read the code yourself — not by default. (Same `superpowers:receiving-code-review` rigor, applied by a cheaper model whose reading doesn't accumulate in the orchestrator.)
   - If there are correctness bugs or convention violations: send the SPECIFIC findings back to `feature-implementer` to fix (not a vague "address the review"), then re-review. That counts as one iteration.
   - **Re-review by resuming the same agents, not by spawning new ones.** Use `SendMessage` with the existing `code-reviewer`'s ID or name to hand it the follow-up diff. It already holds the original diff, the repo's conventions, and its own earlier reasoning, so a re-review costs a short exchange instead of a cold start that re-reads everything from scratch — up to three times per ticket. Same for sending fixes back to `feature-implementer`: resume it rather than re-briefing a fresh instance. Only spawn a fresh reviewer when you deliberately want an unbiased second opinion on a large rewrite.
   - If a failure or finding resists a fix iteration, apply `superpowers:systematic-debugging` (find the root cause first) before burning the next iteration on another guess.
   - If the review is clean (no correctness/convention findings): exit the loop.
   - **Before the third iteration**, if an advisor tool is available, consult it once with the remaining findings and what the previous two fixes tried. Skip this if no advisor is on.
   - If 3 iterations pass and findings still remain: STOP. Do not proceed. Report the unresolved findings to the user and ask how to proceed.

4. **Browser verification (frontend-facing tickets only)** — if the ticket is substantially UI work, prefer `/build-ui-ticket` instead of this command: it dispatches `frontend-dev`, which drives the browser inside the implementer so fixes don't round-trip through the orchestrator. For an *incidental* UI change inside an otherwise backend ticket, verify it here at the orchestrator level (the three agents above have no MCP tools): if the app isn't already running, start it with the project's documented dev-server commands (`## Dev Servers` in `CLAUDE.md`, preferring its lightweight/fixture-backed mode), drive the changed flow with the chrome-devtools MCP tools, and check the brief's acceptance criteria. A failure here feeds back into the fix-loop and counts as an iteration. Skip this step entirely for backend-only work.

5. **Simplification pass (optional)** — only when the brief requests it or the diff turned out large: run the `/simplify` skill on the ticket diff (it reviews the changed code for reuse, simplification, efficiency and altitude, then applies the fixes), then send the simplified result to the existing `code-reviewer` once via `SendMessage`. Like `/code-review`, this runs here at the orchestrator level — subagents have no Skill tool. One pass only — no simplify/review ping-pong.

6. **Report back** — summarise for the caller: what was implemented, which files changed, what tests were added and their pass/fail result, and the final review status (clean / escalated). Apply `superpowers:verification-before-completion`: every claim of "done/passing" must be backed by command output actually captured during this cycle — never assert success you didn't observe. Do NOT start the next task.
   - Include a **docs impact** line: name what this ticket changed that a living overview, a `CLAUDE.md`, or a README will need to reflect — or "none". **This loop does not write documentation** — that is `/write-docs`'s job, and the caller sequences it (`/build-feature` records these lines in `.scratch/<feature-slug>/docs-impact.md` and routes docs tickets there). Do not send `feature-implementer` off to update an overview here.
